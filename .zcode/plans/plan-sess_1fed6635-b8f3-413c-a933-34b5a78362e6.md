## Backend changes (STAGING فقط — لا schema changes، لا migrations)

### 1. `POST /oms/orders/approve-bulk` (ملف جديد `oms-bulk.service.ts`)
- `{ids}` → loop على `approve` الأصلية. غير المؤهلة → `failures` مع السبب. Response موحّد.

### 2. `POST /outbound-orders/bulk/process` — بدون خطة مخفية
- Backend لا يبني plan تلقائيًا. Modal يعرض prefill مرئي (execution mode, requiresPacking, packing/dispatch config) → admin يعدّل ويؤكد → endpoint يستقبل الـ config الصريحة `{items: [{outboundOrderId, executionMode, requiresPacking, packingLocationId?, dispatchDockId?}]}` → loop `updatePlan` + `approveAdmin`، و`assertOutboundAdminPlanComplete` يرفض الخطة الناقصة.

### 3. `POST /outbound-orders/bulk/complete-picking` و `/bulk/complete-packing`
- `{ids}` → loop على الـ services الأصلية (status checks قائمة).

### 4. `POST /outbound-orders/bulk/shipping-details` — Quick Confirm + per-order exceptions
- Endpoint يستقبل `items: [{outboundOrderId, <shipping fields>}]} + excludeIds?`.
- **Prefill**: endpoint جديد `POST /outbound-orders/bulk/shipping-details/preview` يرجع لكل order البيانات الافتراضية المحسوبة (address governorate/city/area، weight/الأبعاد المحسوبة من المنتجات، package type, عدد packages, payer, …) + حالة كل order: `ready` أو `needs_attention` مع سبب (address ناقص / city ناقصة / required field missing / invalid data).
- **الوضع الطبيعي**: لو كل الـ orders جاهزة → زر واحد **"Use Default Details & Continue"**: "100 orders are ready with their default shipping details. Confirm to continue." → اعتماد defaults للجميع بدون فتح كل order.
- **لو فيه مشاكل**: "96 Ready · 4 Need Attention" — الـ 4 تظهر بأسبابها ويقدر الـ admin يعدّلهم **فقط** أو يستبعدهم، بينما الـ 96 تكمل. Bulk edit مسموح فقط للحقول الآمنة للمشاركة (package type/contents/payer)؛ العنوان per-order.
- التنفيذ: loop `saveShippingDetails(per-order payload)` + `completeShippingDetailsAdmin` لأوامر **manual** → `ready_to_ship`. أوامر **carrier** تُترك للـ bulk shipping workflow. فشل order لا يوقف الباقي.

### 5. Mixed-status behavior موحّد
- كل bulk endpoint يُنفَّذ على المؤهل فقط؛ ineligible → `failures` مع السبب. الـ UI: الـ button لا يختفي — `Ship (8 eligible)` + warning أن 2 لن تُنفَّذ، والـ Result Summary يوضح الجميع.

### 6. Duplicate/concurrency protection
- فحوصات status أصلية + idempotency القائمة (`claimPendingShipment`، رفض duplicate ids في `confirmAndStart`) + `@Throttle` على الـ endpoints الجديدة + disable submit أثناء التنفيذ (منع double-click) + اختبارات explicit.

### 7. التأكد أن `GET /oms/orders` يرجع `outboundOrderId` (يُضاف لو ناقص).
