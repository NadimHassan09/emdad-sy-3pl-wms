## 1. What EMDAD is

A Syrian 3PL (third-party logistics) platform: warehouse management (WMS) + e-commerce order management (OMS) + finance/billing, with integrations to Syrian carriers.

- Business flow: a client (merchant) stores products in an EMDAD warehouse. The client enters orders (portal form, Excel import, Sheets page, Google Sheet, or the client API). EMDAD confirms, picks, packs and, at status `ready_to_ship`, EMDAD staff choose the carrier and send. **The client never chooses or sees the carrier, carrier prices, or that third-party carriers exist.** This is company policy.
- Every Syrian governorate/city/neighbourhood is in EMDAD's address hierarchy (14 governorates). No carrier covers everything; areas a carrier does not serve go to another carrier or to **Manual Shipping** (a carrier without integration).

Rules already built:
- Babel serves 10 governorates only (no Raqqa, Deir ez-Zor, Hasakah, Suwayda) — confirmed via API + portal on 2 Nov. It is not an EMDAD defect (client had claimed it was; evidence in DECISIONS §1.1).
- A courier is offered only if the shipment meets its documented limits (weight, COD currency, COD min/max, zone). Zero-priced quotes are never "Best price". Sena is hidden when no zone matches.
- "Best price" compares USD-converted values (300 new SYP can be cheaper than 2.5 USD).
- Sila guidance from Sila itself (client forwarded it): send `recipient.area_id` from `GET /regions/areas?leaf_only=1`; COD `pay_on_delivery.amount` = what the recipient pays including shipping, in the stated currency; before any re-send check `GET /cargos?reference=…`; never poll by courier code; show Sila's `error.message` and keep `request_id`; **do not test on the live account carelessly** — a staging test once reached a real courier.
- COD settlement ("COD remitted") is not sent by any carrier webhook or API. Delivered creates the COD record; remittance is a manual confirmation until carriers expose a feed.

## 5. Currency model (owner decisions 3–5 Nov)

- Clients and EMDAD's own books are **USD only** (orders, COD, fees, invoices, balances).
- The Syrian pound exists only between EMDAD and carriers, and it is the **NEW pound** (1 new = 100 old). The old pound is retired from all screens; a bare "SYP" from a carrier is read as new.
- Each carrier's price stays in the currency/unit that carrier uses; the carrier is the source of truth. Conversions to USD happen per carrier before comparing or computing COD.
- FX rate: admin chooses **manual** (enters the rate) or **automatic** (outside source) with settings for refresh interval, stale limit and a minimum-change threshold. Automatic source = fawazahmed0 currency-api (market rate ~13,000 old SYP/USD) with a jsDelivr mirror; the Syrian Central Bank was tried and rejected (unreachable from the server and it publishes the administrative ~122 rate, not the market rate). Stored rate is old-scale internally; UI shows new SYP.

## 6. Finance and billing model (owner decisions 3 Nov)

- No fixed billing cycle: an admin can invoice any client any day for any period (`/billing/invoices/on-demand`, draft → issue).
- Per-client charge rules: inbound, outbound, OMS orders, storage, EMDAD shipping fee — each optional (`/billing/charge-rules`).
- Fulfillment price is dynamic: base + extra lines × fee + extra kg × fee, per order type.
- An OMS order's fulfillment fee already covers the outbound order it generates: that outbound must not be billed again.
- EMDAD shipping fee = EMDAD's own tariff (shipping fee groups per governorate/city/neighbourhood at `/shipping/fee-rates`), never the carrier price. **If no active rate covers a destination, the order cannot be confirmed — this is intended.** The fee-rates page now warns about uncovered governorates and offers templates.
- Two invoices: client invoice (no carrier names or costs) and internal/admin invoice (carrier cost, EMDAD price, margin; admin can edit carrier price and lines).
- Netting: fees are deducted from the client's COD balance ("you had X, owed Y, remaining Z") via `POST /billing/invoices/:id/settle`; cancelling an invoice returns the deduction. One order can be on one active invoice only.
- Client current account = credit (COD due) / debit (shipping, return fees, other) with running balance; only final shipments (Delivered / Returned) enter the account.
- Not agreed with the client yet, so built behind admin settings / disabled by default: carrier reconciliation, in-transit float indicator, return-fee rule (round trip vs return only), when COD becomes due (delivered vs collected vs remitted). Policies live in `FinancialPolicy` (`/finance/policies`).
